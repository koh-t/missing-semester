「メタプログラミング」とは何を意味しているのでしょうか? これは、コードを書くことや効率よく作業することよりも、むしろ _プロセス_ に関わる一連の事柄をまとめて呼ぶ言葉として、私たちが思いついた中で最良のものでした。この講義では、コードをビルド・テストするためのシステムと、依存関係を管理するためのシステムを見ていきます。学生としての日々の中では、これらはそれほど重要ではないように思えるかもしれません。しかし、インターンシップを通じてより大きなコードベースに触れたり、「実社会」に出たりした途端、至るところでこれらを目にすることになります。なお、「メタプログラミング」は「[プログラムを操作するプログラム](https://en.wikipedia.org/wiki/Metaprogramming)」を意味することもありますが、それはこの講義で使っている定義とは少し異なることを断っておきます。

# ビルドシステム

LaTeXで論文を書くとき、論文を生成するために実行しなければならないコマンドは何でしょうか? ベンチマークを実行し、その結果をプロットし、そのプロットを論文に挿入するためのコマンドはどうでしょうか? あるいは、受講している授業で配られたコードをコンパイルしてテストを実行するためのコマンドはどうでしょうか?

ほとんどのプロジェクトには、コードを含むかどうかにかかわらず、「ビルドプロセス」があります。入力から出力にたどり着くために行わなければならない、一連の操作のことです。多くの場合、そのプロセスには多数のステップがあり、多数の分岐があります。このプロットを生成するにはこれを実行し、あの結果を生成するにはあれを実行し、最終的な論文を作るにはまた別のものを実行する、といった具合です。この授業で見てきた多くの事柄と同じように、この面倒に直面したのはあなたが最初ではありません。そして幸いなことに、助けになるツールがたくさん存在します!

これらは通常「ビルドシステム」と呼ばれ、_たくさん_ の種類があります。どれを使うかは、目の前のタスク、好みの言語、プロジェクトの規模によって決まります。とはいえ、その核心はどれもよく似ています。いくつかの _依存関係_ と、いくつかの _ターゲット_、そして一方から他方へ至るための _ルール_ を定義します。ビルドシステムに特定のターゲットがほしいと伝えると、ビルドシステムは、そのターゲットの推移的な依存関係をすべて見つけ出し、ルールを適用して中間ターゲットを順に生成していき、最終的なターゲットが生成されるまでそれを続けます。理想的には、ビルドシステムは、依存関係が変更されておらず、以前のビルドの結果が利用できるターゲットについては、ルールを不必要に実行することなくこれを行います。

`make` は世の中でもっとも一般的なビルドシステムのひとつで、UNIXベースのコンピュータであれば、たいていどれにでもインストールされています。欠点もありますが、単純なプロジェクトから中規模のプロジェクトまではかなりうまく機能します。`make` を実行すると、`make` はカレントディレクトリにある `Makefile` というファイルを参照します。すべてのターゲット、その依存関係、そしてルールは、このファイルに定義されています。ひとつ見てみましょう。

```make
paper.pdf: paper.tex plot-data.png
	pdflatex paper.tex

plot-%.png: %.dat plot.py
	./plot.py -i $*.dat -o $@
```

このファイル内の各ディレクティブは、右辺を使って左辺を生成する方法についてのルールです。言い換えると、右辺に挙げられているものが依存関係で、左辺がターゲットです。インデントされたブロックは、それらの依存関係からターゲットを生成するための一連のプログラムです。`make` では、最初のディレクティブがデフォルトのゴールも定義します。引数なしで `make` を実行すると、これがビルドされるターゲットになります。あるいは、`make plot-data.png` のように実行すれば、代わりにそのターゲットがビルドされます。

ルール内の `%` は「パターン」で、左辺と右辺で同じ文字列にマッチします。たとえば、ターゲット `plot-foo.png` が要求されると、`make` は依存関係として `foo.dat` と `plot.py` を探します。では、ソースディレクトリが空の状態で `make` を実行すると何が起こるか見てみましょう。

```console
$ make
make: *** No rule to make target 'paper.tex', needed by 'paper.pdf'.  Stop.
```

`make` は親切にも、`paper.pdf` をビルドするには `paper.tex` が必要であり、そのファイルの作り方を示すルールがないことを教えてくれています。では、作ってみましょう!

```console
$ touch paper.tex
$ make
make: *** No rule to make target 'plot-data.png', needed by 'paper.pdf'.  Stop.
```

ふむ、興味深いですね。`plot-data.png` を作るルールは _ある_ のですが、それはパターンルールです。ソースファイル(`data.dat`)が存在しないので、`make` は単にそのファイルを作れないと述べているのです。すべてのファイルを作成してみましょう。

```console
$ cat paper.tex
\documentclass{article}
\usepackage{graphicx}
\begin{document}
\includegraphics[scale=0.65]{plot-data.png}
\end{document}
$ cat plot.py
#!/usr/bin/env python
import matplotlib
import matplotlib.pyplot as plt
import numpy as np
import argparse

parser = argparse.ArgumentParser()
parser.add_argument('-i', type=argparse.FileType('r'))
parser.add_argument('-o')
args = parser.parse_args()

data = np.loadtxt(args.i)
plt.plot(data[:, 0], data[:, 1])
plt.savefig(args.o)
$ cat data.dat
1 1
2 2
3 3
4 4
5 8
```

さて、`make` を実行すると何が起こるでしょうか?

```console
$ make
./plot.py -i data.dat -o plot-data.png
pdflatex paper.tex
... lots of output ...
```

ご覧のとおり、PDFを作ってくれました!
もう一度 `make` を実行したらどうなるでしょうか?

```console
$ make
make: 'paper.pdf' is up to date.
```

何もしませんでした! なぜでしょうか? それは、する必要がなかったからです。`make` は、以前にビルドしたすべてのターゲットが、列挙された依存関係に対して依然として最新であることを確認したのです。これは、`paper.tex` を変更してから `make` を再実行することで確かめられます。

```console
$ vim paper.tex
$ make
pdflatex paper.tex
...
```

`make` が `plot.py` を再実行 _しなかった_ ことに注目してください。その必要がなかったからです。`plot-data.png` の依存関係はどれも変更されていません!

# 依存関係の管理

よりマクロなレベルでは、あなたのソフトウェアプロジェクトは、それ自体がプロジェクトであるような依存関係を持つことが多いでしょう。インストール済みのプログラム(`python` など)、システムパッケージ(`openssl` など)、あるいはプログラミング言語内のライブラリ(`matplotlib` など)に依存しているかもしれません。最近では、ほとんどの依存関係は _リポジトリ_ を通じて入手できます。リポジトリは、そうした依存関係を1か所に大量にホストし、それらをインストールするための便利な仕組みを提供しています。例としては、`apt` ツールを通じてアクセスする、Ubuntuのシステムパッケージ用のUbuntuパッケージリポジトリ、Rubyライブラリ用のRubyGems、Pythonライブラリ用のPyPI、Arch Linuxのユーザー投稿パッケージ用のArch User Repositoryなどがあります。

これらのリポジトリとやり取りするための厳密な仕組みは、リポジトリごと、ツールごとに大きく異なるので、この講義では特定のものの詳細にはあまり立ち入りません。ここで _扱う_ のは、それらすべてが共通して使っている用語の一部です。その最初のものが _バージョニング_ です。他のプロジェクトから依存されるプロジェクトのほとんどは、リリースのたびに _バージョン番号_ を発行します。通常は8.1.3や64.1.20192004のようなものです。バージョン番号は数値であることが多いですが、必ずそうとは限りません。バージョン番号は多くの目的を果たしますが、その中でもっとも重要なもののひとつは、ソフトウェアが動き続けることを保証することです。たとえば、私が自分のライブラリの新しいバージョンをリリースし、そこである関数の名前を変更したと想像してください。私がその更新をリリースしたあとで、誰かが私のライブラリに依存するソフトウェアをビルドしようとすると、もはや存在しない関数を呼び出しているために、ビルドが失敗するかもしれません! バージョニングは、あるプロジェクトが別のプロジェクトの特定のバージョン、またはバージョンの範囲に依存していると宣言できるようにすることで、この問題を解決しようとします。そうすれば、たとえ基盤となるライブラリが変更されても、依存する側のソフトウェアは私のライブラリの古いバージョンを使うことでビルドできる状態を保てます。

とはいえ、それも理想的ではありません! もし私が、ライブラリの公開インターフェース(「API」)を _変更しない_ セキュリティアップデートを発行し、古いバージョンに依存していたどのプロジェクトもそれをすぐに使い始めるべきだとしたらどうでしょうか? ここで、バージョンを構成する数字の各グループが意味を持ってきます。それぞれの厳密な意味はプロジェクトによって異なりますが、比較的よく使われている標準のひとつが[_セマンティックバージョニング_](https://semver.org/)です。セマンティックバージョニングでは、すべてのバージョン番号は メジャー.マイナー.パッチ という形式になります。ルールは次のとおりです。

 - 新しいリリースがAPIを変更しない場合は、パッチバージョンを上げる。
 - 後方互換性のある形でAPIに _追加_ を行う場合は、マイナーバージョンを上げる。
 - 後方互換性のない形でAPIを変更する場合は、メジャーバージョンを上げる。

これだけでも、すでに大きな利点がいくつか得られます。たとえば、私のプロジェクトがあなたのプロジェクトに依存している場合、私が開発時にビルドに使ったものと同じメジャーバージョンの最新リリースを使うことは、そのマイナーバージョンが当時のもの以上である限り、安全な _はず_ です。言い換えると、私があなたのライブラリのバージョン `1.3.7` に依存しているなら、`1.3.8`、`1.6.1`、あるいは `1.3.0` でビルドしても問題ない _はず_ です。バージョン `2.2.4` は、メジャーバージョンが上がっているので、おそらく問題があるでしょう。セマンティックバージョニングの一例は、Pythonのバージョン番号に見ることができます。Python 2とPython 3のコードがあまりうまく混在できないことは、皆さんの多くがご存じでしょう。だからこそ、あれは _メジャー_ バージョンの引き上げだったのです。同様に、Python 3.5向けに書かれたコードはPython 3.7では問題なく動くかもしれませんが、3.4では動かない可能性があります。

依存関係管理システムを扱っていると、_ロックファイル_ という概念に出会うこともあるでしょう。ロックファイルとは、それぞれの依存関係について、_現在_ 依存している正確なバージョンを列挙しただけのファイルです。通常、依存関係を新しいバージョンにアップグレードするには、更新用のプログラムを明示的に実行する必要があります。これには多くの理由があります。たとえば、不要な再コンパイルを避ける、ビルドを再現可能にする、(壊れているかもしれない)最新バージョンへ自動的に更新されないようにする、といったことです。この種の依存関係の固定を極端に推し進めたものが _ベンダリング(vendoring)_ で、これは依存関係のコードをすべて自分のプロジェクトにコピーするというものです。こうすれば、そのコードへのあらゆる変更を完全に制御でき、独自の変更を加えることもできますが、その一方で、上流のメンテナによる更新を、その都度明示的に取り込まなければならなくなります。

# 継続的インテグレーションシステム

より大きなプロジェクトに取り組むようになると、変更を加えるたびに行わなければならない追加の作業がしばしばあることに気づくでしょう。新しいバージョンのドキュメントをアップロードしたり、コンパイル済みのバージョンをどこかにアップロードしたり、コードをpypiにリリースしたり、テストスイートを実行したりと、ありとあらゆることをしなければならないかもしれません。あるいは、誰かがGitHubでプルリクエストを送ってくるたびに、そのコードのスタイルをチェックし、いくつかのベンチマークを実行したいと思うかもしれません。こうした必要が生じたら、継続的インテグレーションに目を向けるときです。

継続的インテグレーション(CI)とは、「コードが変更されるたびに実行されるもの」を指す総称です。さまざまな種類のCIを提供している企業が世の中にたくさんあり、オープンソースプロジェクトには無料で提供されていることもよくあります。大手としては、Travis CI、Azure Pipelines、GitHub Actionsなどがあります。どれもおおむね同じように動作します。リポジトリにさまざまなことが起きたときに何を行うべきかを記述したファイルを、そのリポジトリに追加するのです。圧倒的によくあるのは、「誰かがコードをプッシュしたら、テストスイートを実行する」のようなルールです。イベントが発生すると、CIプロバイダは仮想マシンを1台(またはそれ以上)起動し、あなたの「レシピ」にあるコマンドを実行して、通常はその結果をどこかに記録します。テストスイートが通らなくなったら通知が届くようにしたり、テストが通っている間はリポジトリに小さなバッジが表示されるようにしたりできます。

CIシステムの一例として、この授業のWebサイトはGitHub Pagesを使って構築されています。Pagesは、`master` へのプッシュのたびにJekyllというブログソフトウェアを実行し、ビルドされたサイトを特定のGitHubドメインで公開するCIアクションです。おかげで、私たちはWebサイトをとても簡単に更新できます! ローカルで変更を加え、gitでコミットし、プッシュするだけです。残りはCIが面倒を見てくれます。

## テストについての短い余談

ほとんどの大規模なソフトウェアプロジェクトには「テストスイート」が付属しています。テストという一般的な概念にはすでに馴染みがあるかもしれませんが、実際の現場で出会うかもしれないテストの手法や用語を、いくつか手短に紹介しておきます。

 - テストスイート: すべてのテストをまとめて指す言葉
 - ユニットテスト: 特定の機能を単独でテストする「マイクロテスト」
 - 統合テスト: システムのより大きな部分を実行して、異なる機能やコンポーネントが _一緒に_ 動作することを確認する「マクロテスト」
 - 回帰テスト: _以前_ バグを引き起こした特定のパターンを実装し、そのバグが再発しないことを確かめるテスト
 - モック: 無関係な機能をテストしてしまうのを避けるために、関数、モジュール、型を偽の実装に置き換えること。たとえば、「ネットワークをモックする」「ディスクをモックする」といった具合です。

# 演習

 1. ほとんどのmakefileは、`clean` というターゲットを用意しています。これは `clean` というファイルを生成するためのものではなく、makeで再ビルドできるファイルをすべて片付けるためのものです。ビルドのすべてのステップを「取り消す」手段だと考えてください。上の `paper.pdf` の `Makefile` に `clean` ターゲットを実装してください。このターゲットは[phony](https://www.gnu.org/software/make/manual/html_node/Phony-Targets.html)にする必要があります。[`git ls-files`](https://git-scm.com/docs/git-ls-files) サブコマンドが役に立つかもしれません。そのほかのごく一般的なmakeターゲットの数々は、[こちら](https://www.gnu.org/software/make/manual/html_node/Standard-Targets.html#Standard-Targets)に挙げられています。
 2. [Rustのビルドシステム](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html)で、依存関係のバージョン要件を指定するさまざまな方法を見てみましょう。ほとんどのパッケージリポジトリは、似たような構文をサポートしています。それぞれ(キャレット、チルダ、ワイルドカード、比較、複数指定)について、その種類の要件が理にかなうユースケースを考えてみてください。
 3. Gitは、それ自体で簡易なCIシステムとして振る舞うことができます。どのgitリポジトリでも、その中の `.git/hooks` に、特定のアクションが起きたときにスクリプトとして実行される(現在は無効化されている)ファイルがあります。`make paper.pdf` を実行し、`make` コマンドが失敗したらコミットを拒否する [`pre-commit`](https://git-scm.com/docs/githooks#_pre_commit) フックを書いてください。これにより、ビルドできないバージョンの論文を含むコミットが作られるのを防げるはずです。
 4. [GitHub Pages](https://pages.github.com/)を使って、自動公開される簡単なページをセットアップしてください。そのリポジトリに[GitHub Action](https://github.com/features/actions)を追加して、リポジトリ内のすべてのシェルファイルに対して `shellcheck` を実行するようにしてください([やり方の一例](https://github.com/marketplace/actions/shellcheck)はこちらです)。うまく動くことを確認しましょう!
 5. [独自のGitHub actionを作成](https://help.github.com/en/actions/automating-your-workflow-with-github-actions/building-actions)して、リポジトリ内のすべての `.md` ファイルに対して [`proselint`](https://github.com/amperser/proselint) または [`write-good`](https://github.com/btford/write-good) を実行するようにしてください。それを自分のリポジトリで有効にし、タイポを含むプルリクエストを出して、うまく動くことを確認してください。
